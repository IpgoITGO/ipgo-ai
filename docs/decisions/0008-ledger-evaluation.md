# DA-01 수용 범위·DA-08~13 평가 계약

2026-11-03 사용자 작업 1~4 승인. 실제 LLM·배포·DB 쓰기·외부 공유는 범위 밖이다.

- SQS v1 결과가 900,000 UTF-8 bytes 이하이면 유지한다. 넘으면 전체 v1 JSON을
  gzip(mtime=0)/base64로 감싼 v2를 보낸다. v2 필드: contractVersion=2,
  encoding=gzip+base64, uncompressedBytes, sha256, payload. 해제 상한16MiB,
  wire 상한900,000 bytes. 손상/길이/해시/중첩 버전 오류는 저장·ACK 전에 거부한다.
  서버 decoder를 AI publisher보다 먼저 배포해야 한다. 본 작업은 로컬 검증만 한다.
- 입고일 이전 기록은 날짜/수량을 추정 정정하지 않는다. 원본을 보존하며 해당 SKU의
  해당 파일 전체를 계산 제외한다. 유효 날짜의 단위 기록은 다음 월 연결용으로 보존한다.
  상품 일별 표는 계약의 완전한 격자를 유지하되 해당 SKU 모든 날을 미관측으로 표시한다.
  제외 사유에는 원본 행과 최초 문제 날짜를 남긴다. strict read_ledger 기본 거부는 유지한다.
- BacktestRequest에 settings(ProductSettings[])를 추가한다. real은 누락/중복 설정을
  거부한다. H=leadTimeDays+reviewCycleDays를 추정하지 않는다. mock 호환 기본값은 []이다.
- TUNE=5/1~7/31, TEST 기준일=8~9월/실적 마감10/14, 주7일 간격. TUNE에서
  정책을 고정하고 TEST를 정책 선정에 쓰지 않는다. A/B 공통 사례의 WAPE에서
  A가 B보다 10% 이상 낮을 때 A, 그 외 B. 공통 비교 자료가 없으면 B(기존 기본값).
- 커버는 하루라도 기말0이면 실패, 과잉은 기말>실제 출고합의50%. 최소 배수 중
  커버95% 달성 후보를 선택한다. 전부 미달이면 최고 성공률, 동률이면 작은 배수,
  targetMet=false(사용자 선택). 평가 사례0이면 선택 배수/비율/오차는 null이다.
- MAE=Σ|실제−예측|/N(개), WAPE=Σ|실제−예측|/Σ실제. N=0 또는 WAPE 분모0은 null.
- LOW 예상 출고는 같은 산식·예측 길이의 TUNE 실제/예측 비율 P10~P90을
  예측량에 곱한다(사용자 위임 권장안). 선형 보간 분위수, SKU20건→전체 SKU20건,
  부족하면 null. 중앙80% 경험 범위이며 신뢰구간이 아니다. 7일 미만 미산출,
  7~13일 LOW, 14~27일 또는 커버90% 미만 MEDIUM, 28일 이상+커버90% 이상 HIGH.
  커버 평가가 없으면 HIGH 근거가 없어 MEDIUM이다.
- DA-10 위험 구간은 [0,.1), [.1,.3), [.3,1], 사례20 미만 비율은 null.
  이20건은 운영상 경험 비율 해상도 기준이며 통계적 신뢰도 보장이 아니다.
- DA-12는 같은 시작 재고·관측 출고·기간에서 계산 입고와 실제 입고를 비교한다.
  과거 발주 예정 정보가 없으므로 계산 경로에 미래 실제 입고를 주지 않는다.
  실제 조정은 두 관측 재생에 동일하게 반영하되 미래 예측에는 쓰지 않는다.
  겹치는 창은 독립 표본으로 해석하지 않는다. 실제 잠재 수요가 아닌 관측 출고 평가이다.

구현 수용 한도는 월별 단위일20,000/상품일10,000, 조회150,000행,
H 및 D를 합친 DA07/13 예측 후보16,000, 백테스트 후보16,000이다.
DB NUMERIC은 엔진과 동일한 double precision으로 조회해 Decimal 객체 누적을 줄인다.
한도 전체 조합의 안전성은 보장하지 않으며 실제 검증 조합을 별도로 기록한다.
DA10은 P80/P100/P120의 고유 입고 수량만 집계한다. 같은 수량은 중복 계수하지 않는다.
BacktestResponse의 testPolicyMetric은 고정한 정책의 TEST 결과이며 재선정에 쓰지 않는다.
excessTargetMet은 TUNE 과잉10% 목표이다. targetMet(커버95%)과 구별한다.
Spring은 아직 BACKTEST job 생성/저장을 제공하지 않는다. 이번 연결 검증은 AI HTTP/worker
응답까지이며 Server 변경은 정제/계산 결과 압축 수신 경계에 한정한다.

검증: 기존 인간 손계산 fixture는 보존했고 AI 전체526건·Ruff가 통과했다.
첨부22개월의 정제/압축 발행 형식, 117,640행의 조건부 백테스트와 fake DB 경계의
HTTP 계산을 network=none/x86/2CPU/256MiB/UID10001에서 검증했다. 실제 PostgreSQL,
SQS 배달/ACK, Spring 저장, ARM, 운영 창고 설정·업무 효과·LLM은 이 측정의 범위 밖이다.
월별 정제 최고 cgroup168,648,704bytes, prefix 재사용 후 HTTP31상품의 단독 실행
58.308초/177,942,528bytes였다. 앞선 동시 검증106.339초는 다른 부하 조건이며
후속 성공으로 덮어쓰지 않는다. 단일 조합의 관측이며 60초 SLA/전체 용량 조합 보장이 아니다.
이력 정규화 캐시는 한 함수 호출의 SKU 하나에만 존재하고, 같은 상품·기준일·관측 마감의
H/D 사이에서만 재사용한다. 독립 생성과의 동등성·미래 오염 차단을 검증했다.

PR 검토 보완: settings는 정책·정확도·실제 입고 비교의 평가 대상만 지정하며, 같은 source의
다른 SKU는 위험 pool에 남긴다. 미설정 SKU의 설정 조회 오류로 정상 부분 평가를 거부하지 않는다.
일별 재고 연속/항등식은 절대 오차1e-9개만 허용하며 상대 오차는 사용하지 않는다.
큰 재고에서 수량 차이가 숨지 않도록 입력 거부·HTTP/worker 동등성 회귀를 확인한다.
